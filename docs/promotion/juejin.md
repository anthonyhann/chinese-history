## 开头

做中文历史类应用的开发者应该都有过这种痛：想查个「汉武帝在位多少年」，要么翻维基百科手抄，要么爬百度百科担心版权，要么用 CBDB 被学术格式劝退。

[chinese-poetry](https://github.com/chinese-poetry/chinese-poetry) 用 53.8k star 证明了「JSON 分发的开放数据库」这条路在古诗词领域完全走得通。那历史呢？

我花了几天时间，把这条路在历史领域跑通了：[chinese-history](https://github.com/anthonyhann/chinese-history)。

## 和诗词库有什么不同

历史数据比诗词难在三点，也是这个项目的三个设计决策：

**① 出处强制**。chinese-poetry 最大的痛是数据错了十年没人发现（连《静夜思》都缺）。本项目 CI 直接拒收无出处数据：`sources` 为空 → 校验失败 → 合并不了。

**② 争议多值**。刘邦生年前 256 还是前 247？学术界没定论。我们的答案是都存：

```json
"birth": {"year": -256, "circa": true,
          "disputed": [{"year": -247, "source": "史记集解引皇甫谧等说"}]}
```

**③ 时间双轨**。史料原文纪年（"秦始皇三十七年七月丙寅"）和归一化公历（-210）并存，年号表 551 条做换算引擎。

## 文物图片：能用的直接给图，不能用的只给链接

- 大都会、史密森尼亚洲艺术馆、克利夫兰：**CC0，图片 URL 直接用**
- 大英博物馆：CC BY-NC-SA 禁商用 → 只放官方检索链接
- 台北故宫、吉美：本轮网络/反爬不可达，如实记录在 Release Notes 的「通道勘探表」里

## 工程链路

```
JSON 分片（每文件 ≤1000 条，文件名即索引）
  → tools/validate.py（零依赖 CI：schema + 引用完整性 + 出处 + 图片许可）
  → 打 tag → GitHub Actions 自动构建 SQLite + JSON zip → Release
```

数据本身和构建产物同源：Release 里的 SQLite 由 CI 从 JSON 直接构建，不存在手工同步的中间环节。

## 参与方式

- 用数据：clone 即用，SQLite 在 Release 里
- 捉虫：PR 带出处（这是唯一硬性要求）
- 加数据：从你熟悉的朝代/家乡博物馆开始，一条数据一个 PR

诚实声明：大部分数据 AI 生成 + 人工抽查，`_meta.verified_by` 为空 = 未人工核验，用前核 sources。
